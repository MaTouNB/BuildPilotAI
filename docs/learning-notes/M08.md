# M08 学习笔记：证据决定三态结果

## 数据如何进入规则

原始 CSV 和型号不直接证明兼容。运维审核清单把商品、字段、值/单位、来源网址与定位、查阅时间、审核者、审核状态、递增版本和明确替代关系写入 part_spec_override。只有当前未被已批准后继替代的 APPROVED 证据参加计算。多个不同值没有明确替代时是冲突，返回 UNKNOWN，而不是取最新、最低或任意一个值。

数据库拒绝更新/删除审核记录；修正需要追加。命令按商品锁串行审核并检查版本，整个清单事务提交。幂等依靠固定记录 ID 与完整内容一致性，不是靠名称相同。

## 规则与边界

CPU_SOCKET 比较 CPU 与主板的 socket；MEMORY_DDR 比较内存与主板的 DDR 代际；GPU_LENGTH 用 Decimal 比较 GPU 标称长度是否不超过机箱标称空间。尺寸只接受明确 mm，无单位不猜测。相等长度仅本项 PASS；冷排/线材余量另行检查。

汇总优先级 FAIL > UNKNOWN > PASS。缺组件、未审核、无效单位/数值或冲突都不能通过。CPU 与主板插槽相同不证明 BIOS 支持；三项都 PASS 也不证明整机兼容。

## 私人方案与报告版本

报告走与方案相同的服务端身份/租户/所有者检查，绑定 expected_version；检查短暂锁住方案防止读到半次编辑。查询规格与组件使用一个 SQL statement 快照。报告返回 build_version、规则集版本、时间、证据记录 ID/版本；后续规格审核变化可令同一方案的新报告改变，但不更新原报价快照或方案版本。

装机写请求的幂等重放返回原响应，其中 checked_rules_status 是原操作当时的结果；查询最新报告才能反映后续审核。报告本身不保存为业务变更，也不替 Agent 做变更。

## 三个练习

1. 阅读 tests/test_compatibility.py，解释 235mm 显卡 /235mm 标称空间为何仅本项 PASS，234.99mm 空间为何 FAIL。
2. 给同 CPU 添加 AM5 和 AM4 两条已批准证据；先观察 UNKNOWN，再用明确 supersedes_id 的已批准记录解决冲突。为什么 pending 后继不能隐藏已批准证据？
3. 在隔离测试中令某条规则 FAIL，另一条缺证据；确认汇总 FAIL，同时每条仍保留自己的证据和缺失字段。

运行：根目录 make check、make check-db。真实硬件价格与合成测试完全分开；真实目录缺主板等类别时不声称通过完整装机验收。
